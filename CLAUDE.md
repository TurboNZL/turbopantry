# TurboPantry: project handoff

Read this first, then `PROJECT_BRIEF.md`. This file is the running state and decision log: update it whenever a decision or the state changes.

## Engine
This app is pinned to TurboNZL/turboengine (see `.turboengine.json`; `docs/development/ENGINE.md` says which modules and where they live). The engine is a **reference, not a dependency**: its modules are working code copied into apps. Before building something that every app would want (updates, release naming, the theme picker, window chrome, settings layout, guides), look in the engine's `modules/` first and copy from it rather than inventing a new one. If you improve a module here, say so in the session log so it can be ported back to the engine.

## User preferences (how to work with them)
- Don't waste their usage. Fact-check and double-check yourself; use web search liberally.
- They write casually; reply in normal capitalised prose.
- Put effort into verifying against real runs, not only unit tests.
- A merged PR cannot take new work: restart the branch from main for follow-up changes. Commit trailers as the harness gives them.

## Decisions made (don't re-ask)
| Topic | Decision |
|---|---|
| Naming | The product is written **TurboPantry** (title case) in all docs and UI text. Repositories, packages and file names stay lowercase (`turbopantry`, `.turboengine.json`, lowercase release assets). |
| What | Self-hosted recipe box + shared shopping list. Recipe import modelled on Osta (websites and Instagram); shopping list modelled on AnyList (store categories, one-tap "add recipe ingredients", live sync). |
| Vision | A household kitchen brain: recipes + shared shopping list + a **stock tracker** ("Pantry": what is in the house with quantities, so stocked items are left off the list and a shortfall adds only the difference). Full description in `PROJECT_BRIEF.md`. Roadmap step 3 is now "stock + shopping list together": they share one item model, so do not build the shopping list first and bolt stock on. |
| Pantry and shopping design | The user's decisions (2026-10-15), all built: (1) an item has a DEFAULT amount and a per-item STEP (rough increments, tweakable in the item's settings), a unit, a minimum ("keep at least"), a staple flag, a place, aliases and an optional grams-per-cup. (2) "I cooked this" proposes the recipe's amounts, the user changes or removes anything not used, then confirms; undoable. (3) Unit conversion is optional with three modes on the recipe: as written, metric + cups, metric + grams (NZ: grams for weight things, cups/tbsp/tsp for small things; 250 ml cup, 15 ml tbsp); cup weights only where sources agree (flour 125 g, caster sugar 220 g, butter 250 g, rolled oats 90 g), else left in cups. (4) Matching recipe wording to items happens in the IMPORT flow (and a "Link items" sheet on a saved recipe): the original wording is always preserved, aliases are editable on the item, only an exact same-words match links by itself, and similar items are offered as `broader`/`narrower`/`related` candidates that are NEVER auto-chosen: the kind of ingredient matters (fettuccine is not "pasta"). A line with no match becomes a NEW item (specifics kept, e.g. "Fettuccine pasta"), made untracked so it stays out of the pantry list until stocked. (5) Ticking a list line puts it in stock at once (the logged `stock_applied` makes unticking exact); every stock change is in `stock_log`. (6) Everything is live over SSE (`/api/events`, event per topic: items, list, recipes; client reads it with fetch so the token and Access headers go along; a 25 s comment keeps a Cloudflare Tunnel from closing it). |
| Mobile first | The app must be highly optimised for mobile, simple and predictive: design every screen at 390 px first (bottom nav, 44 px targets, steppers over typing, few taps, offers the next likely action). Check each new screen at 390 px in a real browser before desktop. |
| Recipe display | Amounts are bold in the ingredient list and ingredient names are bold inside the method (`highlightStep`, matched against the recipe's own ingredient names). "Amounts on/off" (device setting `showQuantities`) hides every amount in the list and, where an amount sits right before a mentioned ingredient, in the method; other numbers (times, temperatures) are never touched. Zero minutes mean "not given" and are never shown. Counted units are pluralised ("2 cloves"). Pasted step numbers and headings are cleaned (`cleanSteps`). |
| Logo | Engine `logos` module, current schema: `branding/logo.json` with `emblemColor`; the red ring is fixed by the engine, only the emblem has the app's colour. TurboPantry: emblem `jar`, `emblemColor` `#3ddc97`. Regenerate with `node scripts/gen-icons.mjs --png` (see ENGINE.md for the env vars) and LOOK at `--sheet` before committing. |
| Cost | Must be free to run: no paid API anywhere in the default path. A paid/keyed LLM may only ever be an optional add-on. |
| Clients | Web/PWA first, then the engine's Android shell (WebView, share-sheet target, self-update). No Electron. |
| Users | A few accounts on one server (not multi-household SaaS). Exposed through a Cloudflare tunnel, so real auth on every request, HTTPS assumed, WebSocket/SSE must survive the tunnel. |
| Install | The engine's way for any app with its own server (module `self-hosted-server`): `scripts/install-pi.sh` (git checkout under a `turbopantry` service user, systemd, runs `node --experimental-strip-types src/index.ts`), `scripts/update.sh`, and the owner-only "Update server" button. The user runs their self-hosting on a separate drive (`/mnt/data`): the installer takes `--install-dir` (asked for before anything is installed) and keeps EVERYTHING in that one folder: `app/`, `data/`, `home/` (the service user's home), `pnpm-store/`; it refuses a non-empty folder, NTFS/exFAT/FAT, a `noexec` mount, and a `/mnt/...` path with nothing mounted; the unit has `RequiresMountsFor`. Outside the folder it only adds the system user, the systemd unit, the sudoers file, apt packages, and Node/pnpm if missing. Not a release asset, no tarball, no Docker (the user dislikes Docker; an earlier tarball/Docker pipeline was removed when the engine's update arrived). Do not reintroduce Docker as a default. |
| Owner | The first account made is the owner and the only one who may use `/api/admin/*` (server update). `is_admin` column, migration 3. |
| Cloudflare | Tunnel plus optional Access service token; the web client sends `CF-Access-Client-Id/Secret` on every request when set (Settings > Server). Same-origin web needs no CORS. When the Android shell arrives the server needs CORS for the page origin `http://localhost` (see the engine's cloudflare-access module) and its `AccessProxy`. |
| Repo | turbonzl/turbopantry, pinned to turboengine (`.turboengine.json`). |
| Osta share pages | IMPLEMENTED (`import/osta.ts`, `import/browser.ts`). Links `ostarecipes.com/recipes/<id>` and `/s/recipes/<id>` (tries the pasted form, then the other). The page is a client-rendered React/MUI app on Firebase with NO JSON-LD, so it is rendered in headless Chromium (playwright-core, no download: Chromium comes from the machine, `TURBOPANTRY_CHROMIUM` or `chromium`/`google-chrome` on the PATH; the installer apt-installs `chromium`, `--no-browser` skips) and read by `parseOstaPage`, which uses the stable MUI typography classes (h1 title, h3 headings, subtitle3 ingredient with a quantity span, body2 note), never the generated `css-xxxx` ones. The saved page (fixture `test/fixtures/osta-share-page.html`, the user's .mht) has NO method, so the draft carries a warning and the user adds steps. BUT the user's own screenshots show the live Osta page DOES display a method for other recipes (a "Cook pasta" section with numbered steps): the saved .mht may have been a recipe without one, or the method loads differently. The method selector is UNKNOWN until the user saves a page of such a recipe (ask for it): never guess it. When an Osta description contains the original website's address the draft lifts it out and offers "Import from <site> instead" (`ImportDraft.alternative`): the direct import is cleaner and faster. Osta's own text sometimes has ingredient lines glued into steps ("melt butter20g butter"): that is Osta's data, not ours. Browser lock-down: every request is checked against `OSTA_HOSTS` (ostarecipes.com + the Google services it uses), images/fonts/media are not loaded, one render at a time, 25 s cap. If Osta changes its markup, fix `osta.ts` against a fresh saved page. NOT verified against the real site (unreachable from the sandbox): that `/s/` redirects, that the real page renders in the same wait condition (text `Ingredients`), private-recipe behaviour. Do not read their Firestore directly. |
| Shopping list model | AnyList-style (verified against AnyList release notes/help): typed items auto-categorised (Produce, Dairy...), categories reorderable per store; adding recipe ingredients merges similar items into one with a summed quantity and keeps the source ingredients viewable in item details; arbitrary units; scaling a recipe updates quantities already on the list; item properties (photo, store, price) are inherited from a matching favourite/recent item; favourites + recently used; real-time sync. Store assignment and location reminders are paid AnyList features: store assignment is in scope, location reminders are not. |
| Recipes are shared | Every account on a server sees and can edit every recipe (a household, like Osta's shared folders); `created_by` records who added it. No per-user recipe privacy yet. |
| Website import | Implemented: schema.org Recipe JSON-LD only (handles @graph, type lists, HowToSection/HowToStep, string steps, ISO times, broken JSON). Microdata and a readability fallback are NOT built. The import returns a DRAFT; the user reviews it and saves. Photos are hotlinked, not downloaded (download+cache is a later job). |
| Fetching pages | `packages/server/src/import/safeFetch.ts` is the only code that fetches user-supplied URLs: SSRF-guarded (public addresses only, checked at connect time, redirects re-checked, 5 MB / 15 s caps). Never add another fetch path for user URLs; reuse it. |
| Instagram import | Osta's real method is not public. User confirmed: Osta does NOT watch the video; it reads the caption AND the comments. So: caption + comments -> heuristic parser, free. Video transcription/OCR is a later, optional step. Fetching the caption without a login is NOT verified: Instagram blocks anonymous scraping and yt-dlp usually needs cookies. The sandbox cannot reach Instagram, so this must be proven on the user's own server before the design is locked. Always keep paste-the-caption and share-from-Instagram as the fallback that cannot break. |

## Hard-won gotchas
- The engine's web files do not compile under `noUncheckedIndexedAccess` (markdown.ts etc.): leave it off (`tsconfig.base.json`). Worth a line in the engine's `guides-and-docs` MODULE.md.
- `test` in `vite.config.ts` needs `defineConfig` from `vitest/config`, not `vite`.
- `pnpm add "github:TurboNZL/turboengine#path:/themes"` writes a codeload.github.com tarball (pinned to a commit) into the lockfile, so CI installs it over HTTPS with no SSH. It works because turboengine is public.
- The `Check` workflow runs on pushes to main only (engine convention), and `Release` runs in parallel with it, so a broken main still releases. Deliberate engine behaviour; revisit if it bites.
- `pnpm install --ignore-scripts` is fine: esbuild ships its binary as an optional dependency.
- Screenshots taken right after navigation catch the page-enter fade and look washed out; wait about 1 s.
- The server runs under `node --experimental-strip-types` in dev AND in production (the installer's service file does the same), so it has no build step: no constructor parameter properties, enums or namespaces in `packages/server`. `erasableSyntaxOnly` in its tsconfig enforces it (it was broken once, caught by a real run).
- The installer must never depend on the folder it was started from: `sudo -u <service user>` keeps the caller's cwd, and the service user often cannot read it (a real Pi install failed with `EACCES: scandir '/home/<user>'` from pnpm). The script now does `cd /` at the top and `as_user` runs `cd / &&` first. My sandbox run missed it because it started from `/tmp`: when testing installers, start them from a folder the service user cannot read (e.g. a 700 root folder).
- Do not `pkill -f server.mjs` from the same shell command line: the pattern matches the shell itself.
